# 2026-11-18 · 修复 Issue #145 副作用提交锁竞态与 Issue #147 Windows 共享句柄/64位句柄缺陷

## 1. Issue #145：副作用落盘后 SQLite 写锁争用与冗余写事务收敛

- **根因链条**：
  1. `Dispatcher.dispatch`（`src/tianshu/dispatcher.py`）在 `FileExecutor.execute()` 已将文件落盘后裸调 `self._commit_result(...)`，一旦 `BEGIN IMMEDIATE` 撞上后台心跳或并发连接持锁导致的 `SQLITE_BUSY`（`OperationalError: database is locked`，见历史 CI `run 43576167008`），异常直接越过派发层，与 `_MemoryTarget` 的 `_fail_unknown` 兜底不对称；
  2. 若 `_commit_result` 与 `_fail_unknown` 连续遇到锁忙、随后进入 `AgentLoop._drive` 的 `except Exception -> _finish` 时锁恰好释放，旧 `_finish` 会在 `tool.intent` 尚无 `tool.result` 的情况下把 Run 终结为 `failed / effect_state="none_applied"` 并调用 `leases.release_run()` 静默释放目录租约（违反红线 2/5/11）；
  3. `AgentLoop.resume_run`（`src/tianshu/loop.py`）误用 `str(r)`（`ResourceIdentity(...)` repr）与 `held` 路径集合比较，导致每次 `resume_run` 即使已持有有效目录租约仍发起一次多余的 `LeaseStore.acquire` 写事务；
  4. `renew_claim`（`src/tianshu/jobs.py`）对同库连接拆成 `claims.heartbeat` 与 `leases.renew` 两次独立 `BEGIN IMMEDIATE ... COMMIT`（Windows `PRAGMA synchronous=FULL` 下双倍 `FlushFileBuffers` 写锁占用）；
  5. `TaskStore._run_end_payload`（`src/tianshu/tasks.py`）组装 `run.end.artifact` 时原样拷入恢复补写的 `recovered: True` 扩展键，触碰 `_ARTIFACT` 封闭字段校验。
- **修复决策**：
  1. `_commit_result`、`_fail_unknown` 与 `_write_mcp_unknown` 统一将 `append_many(batch)`、`UPDATE dispatches` 与 `_set_request_state` 收口进同一个外层 `EventLog.transaction()`，根除事件与派发表分两次提交的半提交窗口；`_FileTarget`、`_dispatch_mcp`、`_dispatch_network` 结果提交失败时统一走 `self._fail_unknown(...)`；
  2. `AgentLoop._finish` 收尾前先按已落库 `tool.result` 事件同步 `progress` 副作用计数（防止异常跳过 `_absorb` 后误报 `none_applied`），并同时检查未配对 `tool.intent` / 在途 `dispatches`（`intent`/`executing`）以及本 Run 尚未解除的本地目录 `recovery.blocked`：一旦命中，绝不写终态 `run.end` 或释放目录租约，而是转入 `RUN_RECONCILING` 保留租约（若 `transition` 自身仍遇 `OperationalError` 则原样上抛由 `Worker._settle` 挂起作业）；
  3. `resume_run` 改为取 `r.path` 规范路径比对已持租约；同库 `renew_claim` 合并为单次写事务，并以 SQLite `SAVEPOINT` 包裹 `leases.renew` 保持 `LeaseLost` 回滚半截租约但保留心跳提交的既有语义；
  4. `_run_end_payload` 按 `_ARTIFACT` 契约投影五字段，使 `recover_run` 对账为 `applied` 后的 Run 可被 `resume_run` 正常收尾。

## 2. Issue #147：Windows 共享违规有界重试、64位 `HANDLE` 原型与本地 `unknown` 收束防线

- **根因链条**：
  1. Windows 下杀毒扫描/索引句柄短暂占用目标文件（`WinError 5 / 32 / 33`）时，`fsutil.atomic_write_bytes` 虽有有界退避，但 `LocalBackend.unlink`、`read_bytes` 与 `identity_key`（`os.stat`）均无重试；尤其 `identity_key` 捕获宽泛 `OSError` 退化为 `path:` 键，会把执行侧二次核对期间的短暂锁冲突误判为 `ToolNotAllowed("目标资源的身份已改变")`；
  2. `leases._win_pid_alive`、`_win_pid_started_at` 与 `isolation._pid_alive` 直接调用未声明 `argtypes`/`restype` 的 `ctypes.windll.kernel32`，默认 `c_int`（32 位有符号）会把高位置位的 64 位 `HANDLE`（如 `0x80000124`）符号扩展截断，导致活进程被误判为死亡或取不到启动时间；
  3. 本地目录写工具在运行期落入 `unknown`（已写 `recovery.blocked`）后，`AgentLoop._advance` 仍返回 `"done"` 继续下一轮模型调用，使 `FakeModel` 等后续返回 `end_turn` 时将目录已阻断的 Run 收尾为 `state == "succeeded"`。
- **修复决策**：
  1. 在 `fsutil.py` 抽出共享 `retry_windows_sharing`，仅对 `winerror in {5, 32, 33}` 执行有界退避重试（POSIX `winerror=None` 与 `FileNotFoundError` 零次重试立即返回/抛出），完整接入 `LocalBackend.require_root`、`exists`、`is_file`、`is_dir`、`size`、`list_dir`、`read_bytes`、`unlink` 与 `identity_key`；`identity_key` 仅在 `FileNotFoundError` / `NotADirectoryError` 时退回 `path:` 键；
  2. `leases.py` 与 `isolation.py` 改用 `ctypes.WinDLL("kernel32", use_last_error=True)` 并显式声明 `wintypes.HANDLE` / `DWORD` / `BOOL` / `POINTER` 原型；
  3. `AgentLoop._advance` 对本地路径目标（`isinstance(target, Path)`）产生 `effect_state == "unknown"` 时立即转入 `RUN_RECONCILING` 并返回 `"reconciling"`，保持 MCP 对象级阻断（`str` URI）原有通知模型语义不变；`tests/test_integration_m5.py` 同步钉住审批删除后的 `run["effect_state"] == "applied"`。

## 3. 验证与边界

- 新增 `tests/test_windows_145_147_regressions.py`：以真实第二条 SQLite 连接 + `threading.Event` 屏障复现单次/双次/三次 `SQLITE_BUSY` 与 `recover_run` 对账恢复，验证 `resume_run` 零冗余 `acquire`、`renew_claim` 单事务 + `SAVEPOINT`、瞬态/持久 `winerror=32/5` 与 POSIX 零重试对照、以及真实 `ctypes.CFUNCTYPE` 下 `0x80000124` 句柄无符号透传（含无原型符号扩展负控）。
- 原生 Windows runner 分片表现以对应 PR 的 GitHub Actions required CI 日志为准；CI 通过不代表真实用户 Windows 10/11 或 ARM64 设备实测。
