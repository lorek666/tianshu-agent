# 普通 Chat 缺失游标时停止续跑

普通 Chat 已写入 `model.intent`、但丢失游标时，以首轮输入初始化会遗漏先前的预算、
会话和工具进度，还可能发送新请求。新建 Chat 和没有 Mission 的历史 Chat 使用同一道检查。
这道检查复用 Responses 的事件判别，并沿用已有的 Responses 重建及 Workflow、Goal 缺游标处理。

- 直接续跑在认领和驱动前拒绝，保留已停止的 Run。桌面控制面返回 `conflict`。
- Daemon 在认领显式续跑作业前，于同一事务内重验。审批决定仍独立持久化，驱动拒绝后通过日志报告。
- 桌面控制面对已挂起、但 Run 仍显示 `running` 的 Chat 也返回缺游标冲突。结果已核清时，
  取消复用原有终结路径，由持久化工具结果与回执保留已发生的效果。缺游标时，终态用已提交的
  模型结果汇总已知费用和用量，保留未计账和未知字段。仍有未配对或未核清的
  派发时保留原事件、作业和租约，界面提示使用 `tianshu recover` 核查后再取消。
- Worker 已按队列协议取得失主作业时挂起作业。如果 Run 仍为 `running`，且没有持久模型结果或工具调用记录，Worker 将其转为 `reconciling`，用户可核对后取消。已有结果或工具记录时保留原 Run 状态，由既有恢复流程核查。

定向测试分别覆盖直接续跑、控制面、Daemon 驱动及真实子进程硬退出后的 Worker 接管。
通过暂停后移除派生游标，在模型结果提交前、工具意图提交后、落盘后或回执提交后触发 crashpoint，核对模型和工具事件、
Run 状态、作业认领及取消行为。控制面和前端分别校验可操作的诊断，现有 Responses、Workflow、Goal
和 Run 控制测试验证兼容路径。各命令及实际结果随候选验证记录保留。独立复审、最终本机全量、
GitHub required CI 及原生桌面实测待完成。

普通 Chat 的完整历史重建尚未交付。取得资源后才出现错误的收尾、父子状态收敛，仍需另行实现和验证。
