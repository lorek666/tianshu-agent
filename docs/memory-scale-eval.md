# 千条级检索评测报告（W6，2026-11-14）

> 脚本：[`scripts/eval_memory_scale.py`](../scripts/eval_memory_scale.py) ·
> 设计：[SPEC-N2-EMBEDDING-PROVIDER-2026-11-14](SPEC-N2-EMBEDDING-PROVIDER-2026-11-14.md) §2.4
> 复现：`uv run python scripts/eval_memory_scale.py`（`--json` 机器可读）

## 动机

[现有小样例评测](memory-retrieval-eval.md)（22 query / 25 记忆）Recall@5 双路
都饱和在 1.000——它证明不了「规模上去以后两路还行不行」。本评测把背景干扰
拉到千条量级，回答两个问题：

1. 词面单路（FTS）在多干扰下的名次退化有多严重；
2. RRF 融合常数 `k` 对该数据分布敏不敏感。

## 方法口径

- 背景记忆**确定性合成**（`random.Random(seed)`，正文唯一有断言）；黄金条目
  20 条嵌在背景里；query 固定 20 条（10 词面重叠 + 10 中英混合；**无
  paraphrase**——哈希基线抓不住改写，如实声明）。
- **hybrid 行用的是 hash 基线，没有语义能力**：这组数字说明的是「两路名次
  融合在规模下的行为」，不是「语义召回」。
- k 敏感性是索引层实验：FTS 名次与语义名次各自独立获取后用 `rf_fuse(k=...)`
  纯函数重排；产品路径的 k 固定 60，这里不冒充产品口径。
- 真 provider（`--provider openai`）分数**没有跑**——没有真实端点凭据，
  不编造、不宣称语义收益。

## 实测（2026-11-14，macOS arm64 本机）

| 模式 | N | Recall@5 | MRR |
|---|---|---|---|
| fts | 50 | 1.000 | 0.767 |
| hybrid（hash） | 50 | 1.000 | 0.975 |
| fts | 200 | 0.650 | 0.650 |
| hybrid（hash） | 200 | 1.000 | 0.942 |
| fts | 1000 | 0.650 | 0.650 |
| hybrid（hash） | 1000 | 1.000 | 0.892 |

k 敏感性（N=1000，索引层实验）：

| k | Recall@5 | MRR |
|---|---|---|
| 30 | 1.000 | 0.892 |
| 60（产品默认） | 1.000 | 0.892 |
| 100 | 1.000 | 0.892 |

## 读法（只说数字支持的结论）

- **规模效应是真的**：25 条干扰下两路都饱和；千条干扰下 FTS-only 掉到
  0.650，两路融合（hash 基线）保持 1.000——「饱和样例证明不了能力」的判断
  被证实。
- **k 在该分布下不敏感**（三个点 MRR 逐位相同）：RRF 的平滑常数不是当前
  数据分布的调优对象；换数据分布或换真 provider 后需要重测。
- **不是语义能力证明**：hybrid 赢在「独立名次融合」，黄金 query 全部与期望
  条目词面重叠。真 provider 的语义收益（改写/同义）仍然没有实测数字。
- 分层细节（lexical/mixed 拆分）见 `--json` 输出：N=1000 下 FTS 的 lexical
  Recall@5 只有 0.4，mixed 0.9——词面重叠的方向不影响融合后的结果。

## 没做到的

- 真 embedding provider 的实测分数（需要真实端点凭据）；
- paraphrase 难度（哈希基线天然为零，放进表格只会误导）；
- 千条以上（10k/100k）的耗时与召回上限——脚本规模阶梯可扩，本轮未跑；
- reranker、跨作用域融合调优——另立工单。
