# 数据准入与迁移绑定契约

日期：2026-11-13。**本文件规定后续实现，当前不是交付或测试通过记录。**
首片 `data backup / verify / restore-plan` 的现状见
[数据生命周期记录](DATA-LIFECYCLE-2026-11-13.md)。本契约只收口实际事件库的启动准入、
离线迁移及其证据绑定；实际恢复隔离、容量保护、保留与 GC 仍须后续实现和验收。

## 1. 决策与范围

采用“兼容既有库、收紧实际打开文件的准入”的增量方案。正常产品库的
`PRAGMA user_version=0` 不因本次接线被改成 2；已有 0→1→2 链仍只证明
`migration_log` 的创建与扩展，**不是全产品结构版本**。事件 payload 版本、
记忆投影版本和这条迁移机制版本分别解释，不能相互替代。

考虑并拒绝本片一次性建立完整产品格式、集中初始化所有业务表的方案：当前 store
仍各自建表与补列，authority 又是独立数据库；一次收归会扩大到多个模块和历史夹具，
不能用一个新整数代替这些兼容证据。完整格式须在普通用户发布前另行冻结覆盖范围、
旧库迁移及应用回退矩阵。本片不能据此宣布 G3 完成。

不修改 C1–C5 的字段、事件集合、记忆状态或历史事件。`authority.db`、凭据库及
工作区文件不属于本事件库准入的覆盖范围；维护锁仍只约束合作的当前程序，
不抵抗旧版程序或同 uid 的直接 SQLite 写入。

## 2. 正常连接的准入顺序

1. 按**将要打开的实际数据库路径**取得共享维护准入，覆盖连接的整个生命周期。
   `--data-root` 或旁边另一个 `events.db` 不得替实际 `--db` 作证。
2. SQLite 读取真实 schema、`user_version` 和相关已登记版本与迁移进度。
   已有 WAL 按 SQLite 的正常读取语义处理；活库不得使用 `immutable=1` 忽略 WAL。
3. 准入通过后才设置 journal mode、执行事件 DDL、创建 payload 目录及装配业务 store。
   所有正常 EventLog 打开、后台重连与库调用均走这一前缀，不只检查前台 CLI 一次。

准入检查只读 SQL 与进度文件，不调用 store 构造器、不续做迁移、不改写版本或历史行。
SQLite 打开活 WAL 可能维护自己的锁/SHM，这不等于本契约承诺物理介质零写；
失败验收要求事件、主库逻辑内容、迁移状态与材料不变，不强制 checkpoint、
删除或重建 WAL，不把损坏库重新初始化成空历史。

### 2.1 版本和进度的判定

- 不存在或原本为零字节的新库，只允许按本程序的全新库路径初始化；
  必须先排除非空孤立 WAL/journal、未完成进度或其它历史证据，不能只凭主文件大小判空。
  保持 `user_version=0`，不得据此声称它已运行全产品迁移。
- 无迁移进度的已识别 v0 事件库维持兼容。识别至少核对事件表和版本旁表的可读形状；
  已登记 payload/记忆投影版本为未来值、负值或畸形值时拒绝，不能先补表/补列再报错。
  旧事件缺单行版本按现有 v0 映射读取；旁表本身不可读不能当成全部旧事件。
- v1 是现有机制链的中间版本，普通连接拒绝，要求显式离线迁移。
  v2 仅在相应迁移对象可读且进度自洽时进入兼容路径，不代表其余业务表已冻结。
- 高于 2 或不认识的机制版本拒绝普通连接；错误给出使用匹配程序、备份现场与恢复的路径，
  不建议手改版本号或删除数据库。
- 迁移进度为 `in_progress` 时始终拒绝普通连接，即使最后一步 DDL 已提交。
  `completed` 也必须核对目标、实际文件、已完成步骤及实际版本；合法 JSON 不等于合法进度。
  未知状态、坏类型、重复/越界步骤、矛盾目标或不可读进度一律拒绝。

历史 v0 兼容只承诺验收夹具覆盖的形状，不自动证明任意外部 SQLite 文件、未知业务列、
历史 payload 内容或全部投影正确；各模块原有契约读取校验继续有效。新兼容形状先增加
固定夹具、明确映射和失败探针，不能用“补上默认值”洗白未知历史。

### 2.2 布局边界

普通连接仍检查自定义名称/位置的实际 DB，并保留原有可用布局。
本片 `data migrate` 只接受显式标准根 `ROOT/events.db`；根外 DB、根外材料、
不明链接布局不通过“顺手迁移”支持。标准根进度绑定 canonical 的实际 DB 路径，
不因工作目录或环境变量变化而改绑。自定义 DB 的检查不得读取无关数据根的版本来放行。
迁移目标 DB 必须是根内无符号链接的普通文件，且硬链接计数为 1；不能确定时拒绝维护。
这是避免同文件的另一硬链接名称绕过路径锁的布局限制，不声称普通连接已收敛所有硬链接。
新进度位于实际 DB 旁的 `<数据库文件名>.migration.json`。标准根同时识别旧的
`ROOT/migration.json`，存在时不能忽略；该无文件身份的旧记录只关联 canonical
`ROOT/events.db`，不能被同目录 custom DB 或另一根借用。关联的两份记录矛盾时拒绝，
不扫描全机其它数据根寻找“权威”进度。

## 3. 离线迁移协议

入口：`tianshu data migrate --data-root ROOT --backup BACKUP [--json]`。
成功退出 0；前置拒绝、无法安全续做或执行失败退出 2；故障注入保持退出 77。
命令不停止用户服务、不自动删除库、不恢复备份、不启动 daemon。

1. 核对标准布局并取得实际 `ROOT/events.db` 的**独占**维护准入，持有到迁移与进度收尾完成。
   daemon/host 探活仅作附加诊断，不能代替与所有正常 EventLog 的互斥。
2. 校验完整备份，并证明它是这个实际文件的当前升级前一致点：保存的源路径/别名匹配，
   DB 逻辑内容与材料引用匹配。来自另一根、同一根的过期备份或被替换的备份均拒绝。
   只比较事件数、最高 seq 或“verify 通过”不足以证明这一点。
3. 在任何 DDL 前持久化严格版本化进度，绑定实际 DB 路径、起止版本、迁移计划摘要、
   备份 manifest 摘要和升级前逻辑摘要。续做重新校验这些绑定，再判断可执行的下一步。
4. 每步 DDL、该步机制版本和迁移审计在同一 SQLite 事务提交；事务内不等待模型/网络。
   进度的前/后落盘覆盖各中断点，库内实际提交决定步骤是否已完成。
5. 所有步骤与收尾都可重复执行。只有步骤对象、版本、基线摘要及进度相互一致时才收敛
   完成；自相矛盾的进度不得通过“修正数字”静默采信。历史事件内容与顺序保持不变。

### 3.1 逻辑摘要和续做

摘要使用显式版本化算法，覆盖 SQLite schema 以及各持久表的类型化行值，
顺序稳定、区分 NULL/文本/整数/浮点/二进制，包含投影和索引的持久内容；
不读取主库文件哈希冒充含 WAL 的一致点。只排除本条机制自己允许修改的
`migration_log` 及其索引，不能排除业务账本、记忆、游标或未决记录。
FTS 虚拟表及其持久影子表都在比较范围；仅虚拟行或记忆投影摘要相同不能证明索引保存点
相同。算法遇到不可读表/不支持的 SQL 值类型必须拒绝，不跳过后宣称完整一致。
清单材料仍逐项按备份的路径、大小与哈希核验。

材料范围是当前备份声明的 `artifacts/**`、根 `blobs/**` 和 `memory_blobs/**`；
使用与备份相同的链接/路径拒绝规则。独占下读取源材料 inventory，与备份清单做
**双向集合相等**比较，路径、大小、内容哈希均相等才可继续；不能只核备份列出的文件。
备份之后新添的孤儿 blob、快照 manifest 或其它范围内文件也使旧备份不匹配，
即使它尚未被 DB 引用。`run/`、日志、凭据、工作区、SQLite 连接临时旁文件及本条迁移
自己的进度文件不在材料范围；这些排除不扩大到业务正文或其它持久审计材料。

升级前与备份做完整基线比较；续做时只允许登记步骤产生的 schema/审计变化，
其余内容仍须等于绑定基线。算法版本、排除对象及步骤计划改变时，旧进度不能被当成
新计划续做。hash 不包含不可稳定的当前时间、连接状态或 JSON 对象迭代偶然顺序。

新进度使用 `format=tianshu-migration`、`format_version=2`；状态只允许
`in_progress/completed`。数字字段拒绝 bool、字符串强制转换与负值；
未知字段版本拒绝。旧格式 1 缺少实际 DB/基线绑定，不能直接作为新入口的可续做证据；
保留现场并用匹配版本处理，或在后续有独立验收的显式转换中处理，不能默默升级进度。
正常 v0 且没有进度的用户库不受此旧进度限制。

旧格式 1 的**已完成**状态保留有限普通连接兼容：仅标准 canonical `ROOT/events.db`
及其自身旧进度可使用，必须严格满足 target=2、status=completed、applied_steps=[1,2]、
current_step=null，数字/时间/备份记录类型合法，实际 DB=v2 且两步审计、表/列/索引相符。
此分支只读，不改写旧进度、不新造基线或备份绑定，不能签发新续做许可。
旧格式 1 的 in_progress 即使 DB 已为 v2 仍拒绝普通连接与新续做。

## 4. 类型和模块边界

- 新 `data_state` 轻量模块拥有机制版本常量、严格进度类型/解析和纯校验；
  只依赖标准库与域错误，不依赖 EventLog、backup 或业务 store。
  `migrate` 可重导出现有公共名称，避免存储两份进度判定逻辑。
- 新 `data_admission` 模块提供 `check_connection(conn, db_path)`：
  在已经取得共享准入的真实连接上只读检查并返回；失败抛 `TianshuError` 子类。
  它复用 `data_state`，不导入 migrate、backup、EventLog 或业务 store，避免检查依赖执行器。
- `EventLog` 在准入通过后执行原有初始化。`:memory:` 使用明确的内存库分支，
  不在当前目录生成迁移文件或维护状态。
- `migrate` 仍拥有步骤、进度持久化、事务与报告；普通 `assert_writable` 的旧严格
  helper 不可原样塞入正常启动，因为它会拒绝所有现存 v0。
- `data_cli` 只负责参数、JSON/文本输出、错误脱敏和退出码，不复制版本判定或 hash 算法。
  校验失败输出必须区分“不兼容”“迁移未完成”“进度损坏”“备份不匹配”“维护忙”。

## 5. 独立验收

1. 用真实库/CLI覆盖新空库、v0、v1、v2、未来版本、坏/未来记忆与 payload 版本、
   坏 JSON 以及合法但矛盾的 completed/in_progress 进度。拒绝发生在 WAL 设置与 DDL 前，
   失败前后逻辑内容和材料摘要不变。整个 event_versions 表缺失时，关闭再重新打开也须
   拒绝，不能通过新建空旁表把原 v1 行洗成 v0；保留整个表存在、单行未绑定的合法 v0 正控。
2. 放置无关根的 v2 `events.db`，以实际 `--db` 指向 v999 的另一个文件；
   CLI、普通 EventLog 及后台重开都须拒绝该实际文件，不新增业务表或 payload 目录。
3. 真子进程持共享连接并停在屏障时迁移拒绝；迁移持独占时正常打开拒绝；
   真硬退释放准入。不得使用同进程两连接冒充跨进程竞争。
4. 异根备份、同根过期事件、相同事件但不同投影/内容、manifest 被替换、
   未登记到 DB 的新增范围内材料、进度绑定被改均拒绝。正控包含未 checkpoint 的
   已提交 WAL，不能因只读模式漏事务；硬链接 DB 在创建进度或备份前拒绝维护。
5. 通过真实 CLI 在 `migration-before-step-1/after-step-1/before-step-2/after-step-2`
   四点硬退并幂等续做；普通连接在中间态拒绝。重复完成不重写历史事件，
   append-only 触发器仍成立；磁盘写进度/DDL失败不能报告 completed。
6. 复审由第二读者亲跑负控与关键探针，绑定最终源码/测试对象及原生平台 CI。
   首片已有绿色、作者自查、只读取日志均不充当新迁移实现验收。

## 6. 后续恢复设计的约束

实际恢复另起实现与契约切片。选定的最小形状是**整个恢复批次的持久执行隔离**：
复制并核对后先隔离，所有普通 EventLog 打开均拒绝；专用只读复核入口检查旧记忆、
游标、摘要/原文、未决 intent、审批和租约。解除时绑定完整恢复材料、实际 DB 身份和
复核范围摘要，不自动启动服务。这样首次启动、重开或 rebuild 都不能绕过隔离，
也不会只挡新检索却放过旧游标中的正文。

整批复核不是“后续删除记录完整”的证明，不提供 unknown 重试授权；
仍保持 `later_forget_delete_history=completeness_unproven`，明确告知恢复点之后的遗忘/
擦除/删除可能无法取得。逐条激活、跨路径恢复、物理擦除历史事件都不属于该最小形状。
隔离权威记录、原子发布、同批续做/清理与专用复核按[受管导入 B 契约](restore-held-contract.md)实施；该契约当前只有文字复审，全部产品验收 `NOT_RUN`。
不能仅 UPDATE `memories.status`，也不能把一个可丢失的投影当作持久隔离。

契约文字不改变当前 `restore-plan` 的只读、`apply_supported=false` 行为。
