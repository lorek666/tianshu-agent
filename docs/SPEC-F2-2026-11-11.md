## 0. 一句话

F2 的 P0 不是"实现沙箱"，而是把三件事做成**可执行、可测、不可静默放宽**的机制：

1. 后端可选；选了做不到的后端必须 `unsupported`，**绝不回落到 local**；
2. 请求隔离边界必须用**实测报告**通过——声明不算，`unknown` 一样拒绝；
3. 每次未隔离执行都必须被如实标成「受信任执行」：**审批前**用户就要看到，
   执行后结果 / 事件 / UI 都要能对账。

同轮把 `TECH-ARCH.md` §6 里"L3a / L4 已交付"这句不成立的话改成事实，
并把 Windows 进程树的降级写清楚。

## 3. 交付增量（三个 PR，按顺序）

### PR A（分支 `feat/f2-seam`，PR #108）：执行后端注册表与 `unsupported`

**目标**：让"用哪个后端"成为进程级可配置、可枚举、可拒绝的事实；产品路径只经过注册表。

新增 `src/tianshu/exec_backends.py`：

```python
EXEC_BACKEND_ENV = "TIANSHU_EXEC_BACKEND"
DEFAULT_EXEC_BACKEND = "local"
UNIMPLEMENTED_EXEC_BACKENDS: Mapping[str, str]   # 名字 → 如实理由

class ExecBackend(Protocol):
    capabilities: ExecBackendCapabilities
    def spawn(self, argv, *, cwd, env, policy, blob_dir=None, pty=False) -> ExecResult: ...

def register_exec_backend(backend, *, name=None, replace=False) -> str
def available_exec_backends() -> tuple[str, ...]
def configured_exec_backend_name() -> str
def exec_backend(name: str | None = None) -> ExecBackend
def reset_exec_backends() -> None      # 只给测试（docstring 标明）
```

规则：

- `exec_backend("local")` → `LOCAL_EXEC_BACKEND`；注册表键稳定为 `"local"`，
  平台差异在 `capabilities.name`（`local-posix` / `local-windows`）。
- `app_container` / `container` / `seatbelt` / `landlock` 与拼错的名字
  → `PolicyUnsupported(backend=名字, feature="exec_backend")`。**绝不回落到 local。**
- 注册纪律（复审整改后）：
  - 同名已存在 → 拒绝，除非 `replace=True`；
  - `spawn` 签名在**注册期**核验（缺 `cwd/env/policy`、或带调用方不会传的必填
    参数 → `TianshuError`），坏签名不会拖到第一次执行才炸成 unknown；
  - 未实现清单里的名字要注册真实实现，必须 `replace=True` **且**
    `capabilities.name == 注册名` **且** `capabilities.isolation` 与名字相称
    （`app_container`/`seatbelt`/`landlock` → `app_container`，`container` →
    `container`）——否则本地后端挂个 `container` 的注册名就能绕过"如实分级"。
  - **注册即代码信任**：注册/替换/重置是宿主代码能力，不是配置或模型可触及的
    接口；测试替身（如 `ContainerDouble`）只证明"接缝能接住一个自称 container
    的实现"，**不证明容器隔离**，不能当成 F2-c2 已交付的证据。

**接线（改动文件）**

- `tools.py`：`ToolContext.exec_capabilities` → `ToolContext.exec_backend`；
  `_run_command` 用 `backend = ctx.exec_backend or exec_backend()`；
  判定顺序与 `exec.spawn()` 逐条一致：
  1. `check_spawn()` 恒做（argv deny 先于 allow → cwd → 上限 → env）；
  2. 只有**本次请求** `pty=True` 时才判 `policy.allow_pty` 与
     `check_capabilities()`（`allow_pty` 是许可，不是"这次要用 PTY"）。
  **反例（复审抓到的真实回归）**：无条件 `check_exec()` 会把
  `allow_pty=True` 读成"本次用 PTY"，于是"策略允许 PTY、后端无 PTY、本次走管道"
  的正常命令被拒，而 dispatcher 预检只在 `args.pty` 时查能力 → 预检放行、执行拒绝。
- `tools.FileExecutor`：参数 `exec_capabilities` → `exec_backend`；
  - `_exec_backend_pinned` 区分"装配层显式指定"与"自己解析的默认后端"；
  - 默认解析的那条路径在**执行前**再核 `resolve_exec_backend() is self._exec_backend`，
    被换掉就 `ToolNotAllowed`（与文件后端 `sandbox.configure_backend` 同一纪律）；
  - **pinned 边界**：`exec_backend=` 显式传入时由装配层（`Dispatcher`）保证
    "预检与执行同一个"；直接构造 `FileExecutor(exec_backend=...)` 属于代码级信任，
    与注册表同级，不是模型/配置接口。
- `dispatcher.py`：删掉 `LOCAL_EXEC_CAPABILITIES` import；构造期解析一次
  `self._exec_backend`（配置错误启动即炸）；`_precheck_exec` 用它；
  `Dispatcher(executor=...)` 传入自定义执行器时**核它的 `exec_backend` 与
  `self._exec_backend` 是同一个对象**（否则预检/执行分裂）。
- `exec.py`：`LOCAL_EXEC_BACKEND` / `LOCAL_EXEC_CAPABILITIES` 保留导出。

### PR B（分支 `feat/f2-isolation-gate`）：隔离请求、实测门、审批前可见与「受信任执行」

**目标**：把 `isolation.py` 的实测门接进执行路径，并把"未隔离"如实写进
**审批请求、执行结果、事件、UI**。

#### B.1 策略字段

`ExecPolicy.isolation_requires: tuple[str, ...] = ()`：PRD §8.1.1 的四边界名，
`()` = 不声明隔离要求。构造时校验 ∈ `ISOLATION_BOUNDARIES`、去重保序；
`to_dict()` / `from_dict()` 带上。

CLI：`task create --allow-exec-cmd ... --require-isolation files_authority`
（可重复；choices = 四边界名；没配 exec 策略却给隔离要求 → `ValueError`，
不允许造一个全拒策略却假装"已配置"）。
控制面：`task.create` 参数 `require_isolation: list[str]`，同口径校验。

#### B.2 实测门（边界独立）

`isolation.py` 新增：

```python
ISOLATION_LEVEL_BOUNDARIES = {           # 只用于视图显示，不是门的判据
    "none": (),
    "path_only": (ISOLATION_BOUNDARY_FILES,),
    "process_tree": (ISOLATION_BOUNDARY_FILES, ISOLATION_BOUNDARY_PROCESS_TREE),
    "app_container": ISOLATION_BOUNDARIES,
}
def measured_level(report) -> str          # 只按 enforced 判定（累计语义）
def isolation_view(backend, report=None) -> dict
def probe_backend_cached(backend, *, workspace, data_root, timeout_ms=..., refresh=False)
def require_isolation_requirements(policy, backend, *, workspace, data_root, report=None) -> None
```

语义（复审整改后的唯一口径）：

- **门按"请求的边界逐条"判定**，边界之间**独立**：请求 `process_tree` 只要求
  杀树有实测，不隐含 files。这一点写进 `isolation_requires` 的 docstring。
- `isolation_view.level` 是**累计显示**（`measured_level`），与门的判据分开：
  可能出现"门放行 `process_tree` 但 level=none"——此时视图必须带
  `boundaries`（逐边界状态）与 `enforced_boundaries`，UI 显示
  "部分边界已实测（process_tree）；其余仍属受信任执行"，不能只说"受信任执行"
  也不能只说"已隔离"。
- 要求非空时**必须有实测报告**：`probe_backend_cached(backend, workspace=..., data_root=...)`；
  任何 `unknown` / `not_enforced` → `IsolationRefused`，发生在 **spawn 之前**。
- **报告缓存条目 = `(后端对象本身 identity, PROBE_VERSION, platform_label(),
  解析后的 workspace, 解析后的 data_root, timeout_ms)`**。理由：
  - `files_authority` 探针的证据依赖 `data_root`（`isolation.py:330-340` 在它下面
    建"工作区外文件"与权威库探针），只按后端+平台缓存会把另一个数据根的证据
    当成这个任务的证据；
  - **绑定后端对象 identity**（不是只绑名字）：`register_exec_backend(replace=True)`
    或 `reset_exec_backends()` 之后 `exec_backend()` 返回的是另一个对象，缓存自然
    失效并重新探测——否则同名新实现会继承旧实现的 `enforced`。
- `data_root` 接线：`ToolContext` 增加 `data_root: Path | None`；
  `FileExecutor` 从 `tasks.data_root` 填；`Dispatcher._precheck_exec` 用
  `self._data_root`。执行路径没有 `data_root` 时**不探测、直接拒绝**要求
  （没有证据就拒绝），绝不退回临时目录假装测过。
- **报告本身绑定探测现场与归属**：`IsolationReport` 增加
  `workspace: str` / `data_root: str` / `probe_version: str`
  （`probe_backend()` 填解析后的路径；`PROBE_VERSION` 是探测逻辑版本常量）。
  `require_isolation_requirements(..., report=...)` 只接受**五项全部一致**的报告：
  `report.backend == 本次后端名`、`report.platform == platform_label()`、
  `report.workspace/data_root` 与本次解析路径一致、`probe_version` 为当前版本；
  任何一项不一致或未绑定 → `IsolationRefused`（"报告不是这次现场的证据"）。
  **只核现场不核后端/平台**会让"本地后端的 enforced"给另一个后端发通行证
  （复审用假后端传 `local-posix` 报告复现）；缓存键的 identity 只保护缓存路径，
  直塞 `report` 的公开入口仍会绕过。
- **`FileExecutor.data_root` 允许 `None`**：没有数据根是合法状态（`TaskStore`
  的 `data_root` 本来就是可选）。构造/普通执行不能因为 `None` 崩；只有
  **声明了** `isolation_requires` 的执行才在门里拒绝（"无法产出绑定现场的报告"）。

#### B.3 审批前可见（复审补的硬要求）

PRD §8.1（`docs/PRD-v1.md:1041`）："批准启动一个程序，不等于对其后续所有行为
作出可撤销保证""用户必须看到真实权限范围"。所以标签必须在**批准之前**出现：

1. `dispatch.requested` payload 增加**可选** `isolation` 对象（B.7 的形状）；
   只对 `action == "exec"` 写入——exec 走的是审批路径（`c4.exec` 恒需人工），
   非 exec 的 auto 请求没有"执行隔离"这个语义，字段缺席而不是写 `null`；
2. `approval.requested` payload 同样增加可选 `isolation`——由
   `ApprovalStore.request(..., isolation=None)` 接收（dispatcher 传入装配层
   解析的后端视图），写入事件；
3. `ControlPlane._approval_rule_ids()`（`control.py:529`）扩展为
   `_approval_context()`：从 `approval.requested` 事件同时回读 `rule_id` 与
   `isolation`；
4. `approval_view(..., isolation=None)` 增加 `isolation` 字段（**契约变更**：
   `tests/test_control.py` 的精确字段集合断言同轮更新）；
5. `ui/src/api/types.ts` 的 `ApprovalView` 增加 `isolation`；
   `ApprovalCard` 在动作下方显示人话（复用 B.7 的映射），不再让用户在

#### B.7 视图形状与 UI 优先级

```python
{"backend": "local-posix", "declared": "none", "measured": None,
 "level": "none",                     # 累计显示（报告优先，声明不产生等级）
 "unverified": True,                  # 没有报告
 "contradicted": False,               # 声明与实测不一致（报告胜出）
 "boundaries": {"files_authority": "not_enforced", ...},
 "enforced_boundaries": ["process_tree"]}
```

UI（`humanize.ts`）优先级**必须**按此顺序，否则会掩盖更严重的状态：

1. `contradicted` → 「后端自述 {declared}，实测 {measured}」（tone=warn）；
2. `unverified` 且 `declared != "none"` → 「后端自述 {declared}，未实测」（warn）；
3. `level == "none"` 且有 `enforced_boundaries` → 「受信任执行：整体未隔离；
   仅「X」边界有实测证据」（warn）。**不能**写成"已实测的边界：…"——那容易被
   读成"部分隔离 = 更安全"；PRD §8.1 要的是真实权限范围，不是分数；
4. `level == "none"` → 「受信任执行：未隔离」（warn）；
5. 其它 → `ISOLATION_LEVEL_LABELS[level]`，未知值兜底「隔离情况未知」。

`ui/src/lib/humanize.ts` 增加 `ISOLATION_LEVEL_LABELS` / `isolationSentence()`，
`tool.result`、`dispatch.requested`、`ApprovalCard` 共用同一函数。

## 6. 未验证（必须进验收报告）

- Windows **实机**：无；Job Object 未实现，进程树仍 `unknown`。
- macOS x64 / Linux x64 / arm64：无实机，矩阵保持 `unknown`。

  执行结果里的视图才是本次执行的证据。
- 报告缓存只覆盖 `(后端对象 identity, PROBE_VERSION, 平台, workspace, data_root,
  timeout)`，跨进程不共享。
- **旧 v1 二进制读新库不支持**（新增可选字段 + `additionalProperties:false`）；

## 7. 不在范围（含决策理由）

- **不实现** Seatbelt / Landlock / AppContainer / 容器：PRD F2 已定调。
- **本轮不实现 Windows Job Object**，理由是**选择不做**，不是"做不到"：
  1. 技术上可行：`Popen(..., creationflags=CREATE_SUSPENDED)` 得到暂停进程，
     用 `Popen._handle` 先 `AssignProcessToJobObject`，再用 `NtResumeProcess`
     （或枚举线程 `ResumeThread`）恢复——即使不重写 `Popen` 也只依赖
     **私有/未文档化**接口与 `ctypes`；
  2. 但本机**没有 Windows 实机**，唯一验证渠道是 CI runner；用私有接口写
     进程控制、且无法证明 assign 窗口零逃逸，属于"不可证明的隔离"，
     与"可证明才能声明"的纪律冲突；
  3. 真要做得按工单推进：完整 `CreateProcess`（或私有 `_handle` 路线）+ Windows
     实机验收 + Job 事件观察，单独排期，不在本轮假装。
  → 本轮 Windows 如实保持 `supports_job_objects=False`，矩阵写 ⛔。
- **不做** per-run 后端选择（进程级；理由同 `sandbox.py` 的 `loop.py` 判据）。
- **不做** memory / 网络 / MCP 的隔离（不同域，各自工单）。
- **不做** UI 独立"隔离"面板：本轮只到审批卡片与时间线文案（写进未验证）。

## 9. 风险与决策规则

- R1 探针在 dispatcher 进程跑：用真实 `data_root` 下的一次性临时目录，不碰事件库

  存在 → 常量保留，不受影响。

  `ApprovalView` 要改 `ui/src/api/types.ts`，事件 payload 只需读取。
- R4 **契约封闭对象**（`_EXEC_POLICY` / `dispatch.requested` / `approval.requested`）
  改字段必须同轮改 Python + `schemas/c3/event.json`，否则镜像测试直接红。
- **决策规则（硬）**：任何 `unknown` 只能拒绝；任何"声明"都不能发通行证；任何失败都
  不能回落到更宽松路径；任何"没测过"都只能进未验证清单。违反其一视为没做完。
