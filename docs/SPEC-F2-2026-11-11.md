## 0. 一句话

F2 的 P0 不是"实现沙箱"，而是把三件事做成**可执行、可测、不可静默放宽**的机制：

1. 后端可选；选了做不到的后端必须 `unsupported`，**绝不回落到 local**；
2. 请求隔离边界必须用**实测报告**通过——声明不算，`unknown` 一样拒绝；
3. 每次未隔离执行都必须被如实标成「受信任执行」，并进入工具结果 / 事件 / UI。

同轮把 `TECH-ARCH.md` §6 里"L3a / L4 已交付"这句不成立的话改成事实，
并把 Windows 进程树的降级写清楚。

## 3. 交付增量（三个 PR，按顺序）

### PR A（分支 `feat/f2-seam`）：执行后端注册表与 `unsupported`

**目标**：让"用哪个后端"成为进程级可配置、可枚举、可拒绝的事实；产品路径只经过注册表。

新增 `src/tianshu/exec_backends.py`：

```python
EXEC_BACKEND_ENV = "TIANSHU_EXEC_BACKEND"
DEFAULT_EXEC_BACKEND = "local"
UNIMPLEMENTED_EXEC_BACKENDS: Mapping[str, str] = {...}   # 名字 → 如实理由

class ExecBackend(Protocol):                # runtime_checkable
    capabilities: ExecBackendCapabilities
    def spawn(self, argv, *, cwd, env, policy, blob_dir=None, pty=False) -> ExecResult: ...

def register_exec_backend(backend, *, name=None, replace=False) -> None
def available_exec_backends() -> tuple[str, ...]
def configured_exec_backend_name() -> str     # 读 env，默认 "local"
def exec_backend(name: str | None = None) -> ExecBackend
def reset_exec_backends() -> None             # 只给测试
```

规则：

- `exec_backend("local")` → `LOCAL_EXEC_BACKEND`；`capabilities.name` 仍是平台名
  （`local-posix` / `local-windows`），注册表键是稳定的 `"local"`。
- `exec_backend("app_container" | "container" | "seatbelt" | "landlock")`
  → `PolicyUnsupported(backend=名字, feature="exec_backend")`，理由写明"v1 未实现，
  见 TECH-ARCH §6 / isolation-matrix"。**绝不回落到 local。**
- 拼错的名字同样 `PolicyUnsupported`，消息列出 `available_exec_backends()`。
- 注册同名 → `TianshuError`（`replace=True` 才允许）；注册真实实现时从"未实现清单"
  移除该名字——这是未来容器后端的接入口。
- 注册时核验：`capabilities` 是 `ExecBackendCapabilities`、`spawn` 可调用；核不过抛。
- 不缓存解析结果：env 改了下次立即生效（daemon 重启语义简单）。

**接线（改动文件）**

- `tools.py`
  - `ToolContext.exec_capabilities` → `ToolContext.exec_backend: ExecBackend | None = None`。
  - `_run_command`：`backend = ctx.exec_backend or exec_backend()`；**先**
    `check_exec(policy, backend.capabilities, argv, target, child_env)`，**再**
    `backend.spawn(...)`。策略核验留在调用方，不依赖后端自觉（完整后端会再核一次，
    两边看到的必须是同一个世界）。
  - 输出 `policy` 增加 `backend` 与 `declared_isolation`。
  - `FileExecutor.__init__(exec_capabilities=...)` → `exec_backend: ExecBackend | None = None`，
    解析一次并在执行前再核"没被换掉"（与 `sandbox` 后端同一纪律）。
- `dispatcher.py`：删掉 `LOCAL_EXEC_CAPABILITIES` import；`Dispatcher.__init__` 增加
  可选 `exec_backend`，`_precheck_exec` 用 `self._exec_backend.capabilities`，
  `FileExecutor(...)` 传同一个后端。
- `exec.py`：`LOCAL_EXEC_BACKEND` / `LOCAL_EXEC_CAPABILITIES` 保留导出（兼容 import），
  产品路径不再直接引用。

**判据 ↔ 测试**（新文件 `tests/test_exec_backends.py`）

| 测试名 | 钉住什么 |
|---|---|
| `test_default_backend_is_the_local_backend` | 默认解析到 `LOCAL_EXEC_BACKEND`（同一对象） |
| `test_env_selects_registered_backend` | `TIANSHU_EXEC_BACKEND` 生效 |
| `test_unimplemented_backend_is_unsupported_not_local` | 四个未实现名字 → `PolicyUnsupported`，不回落 |
| `test_unknown_backend_is_refused_with_available_names` | 拼错也拒绝，消息列出可用名字 |
| `test_run_command_uses_registered_backend` | RecordingBackend 计数：spawn 走了它，本地 spawn 0 次 |

### PR B（分支 `feat/f2-isolation-gate`）：隔离请求、实测门与「受信任执行」标签

**目标**：把 `isolation.py` 的实测门接进执行路径，并把"未隔离"如实写进结果/事件/UI。

**契约**

1. `ExecPolicy.isolation_requires: tuple[str, ...] = ()`：PRD §8.1.1 的四边界名，
   `()` = 不声明隔离要求。构造时校验 ∈ `ISOLATION_BOUNDARIES`、去重保序；
   `to_dict()` / `from_dict()` 带上；`event_schema._EXEC_POLICY` 增加**可选**
   `isolation_requires: _arr(_s())`——**不加进 required**（旧日志/旧任务没有该字段必须仍合法）。
2. CLI：`task create --require-isolation files_authority`（可重复，choices = 四边界名）；
   没配 exec 策略却给 `--require-isolation` → `ValueError`（不允许造一个全拒策略
   却假装"已配置"）。
3. 控制面：`task.create` 参数 `require_isolation: list[str]`，同口径校验。
4. `isolation.py` 新增：

```python
ISOLATION_LEVEL_BOUNDARIES = {
    "none": (),
    "path_only": (ISOLATION_BOUNDARY_FILES,),
    "process_tree": (ISOLATION_BOUNDARY_FILES, ISOLATION_BOUNDARY_PROCESS_TREE),
    "app_container": ISOLATION_BOUNDARIES,          # 四边界全过才算
}
def measured_level(report) -> str                    # 只按 enforced 判定
def isolation_view(backend, report=None) -> dict     # 进输出/事件
def require_isolation_requirements(policy, backend, report=None, *,
                                   workspace=None, data_root=None) -> None
def probe_backend_cached(backend, *, workspace=None, data_root=None) -> IsolationReport
```

`isolation_view` 形状：

```python
{"backend": "local-posix", "declared": "none", "measured": None,
 "level": "none", "unverified": True, "contradicted": False,
 "boundaries": {"files_authority": "not_enforced", ...}}
```

判定语义：

- `level`：有报告时 `measured_level(report)`；无报告时恒 `"none"`——**声明不产生等级**。
- `unverified`：没有报告时为真；`declared` 与 `measured` 不一致 → 报告胜出并带
  `contradicted: true`。
- 要求非空时**必须**有报告（`probe_backend_cached`），逐条
  `require_isolation(backend, boundary, report)`；任何 `unknown` / `not_enforced`
  → `IsolationRefused`。失败发生在 **spawn 之前**，不存在"退回不隔离"的分支。

**接线**

- `tools._run_command`：`check_exec` 之后、`backend.spawn` 之前调用
  `require_isolation_requirements(...)`；输出恒带 `isolation` 字段（无要求时用声明、
  `unverified=True`；有要求时用报告）。`IsolationRefused` 是 `PolicyUnsupported`
  子类，既有 `except` 分支覆盖 → `c4.exec_unsupported`。
- `dispatcher._precheck_exec`：同样在**审批之前**跑一次（用户不能为注定跑不了的
  命令签字）。
- `ui/src/lib/humanize.ts` `tool.result` 分支读 `output.isolation`：
  - `level === "none"` → 句子后缀「（受信任执行：未隔离）」；
  - `unverified && declared !== "none"` → 「（隔离级别为后端自述，未实测）」tone=warn；
  - `contradicted` → 「（自述 X，实测 Y）」tone=warn；
  - 新增 `ISOLATION_LEVEL_LABELS` 中文映射，未知值兜底「隔离情况未知」。

**判据 ↔ 测试**（新文件 `tests/test_isolation_gate.py`；注入报告避免每用例真跑探针）

| 测试名 | 钉住什么 |
|---|---|
| `test_default_policy_requires_nothing` | `()` 不要求，默认路径 0 成本 |
| `test_unknown_boundary_is_rejected_at_construction` | 非法边界名构造即拒绝 |
| `test_process_tree_requirement_passes_with_measured_evidence` | 真探针一次：POSIX `process_tree` enforced → 放行 |
| `test_unproven_boundary_is_refused` | `not_enforced` / `unknown` → `IsolationRefused` |
| `test_declared_isolation_is_not_evidence` | 假后端自述 `app_container`、探针不通过 → 拒绝 |
| `test_requirement_blocks_before_spawn` | 未满足时后端 spawn 计数 0；`ToolResult.rejected`，rule `c4.exec_unsupported` |
| `test_run_command_output_carries_isolation_view` | 输出字段齐全、`level=none`、`unverified=True` |
| `test_report_is_cached_per_process` | 二次调用不再 spawn 探针 |
| `test_require_isolation_roundtrips_through_task_contract` | CLI / 控制面 → `task.exec_policy.isolation_requires` |
| `test_task_created_accepts_both_policy_shapes` | 老 payload（无字段）与新 payload 都合法 |

**负控**

- N1 判定改成"只看 `capabilities.isolation`" → `test_declared_isolation_is_not_evidence` 必红。
- N2 未满足时 `return` 而不抛 → 拒绝类用例 + `test_requirement_blocks_before_spawn` 必红。
- N3 删掉输出里的 `isolation` 字段 → 输出用例 + UI 用例必红。
- N4 UI 把 `none` 显示成"已隔离" → `humanize.test.ts` 必红。

**UI 测试**（`ui/src/lib/__tests__/humanize.test.ts` 新增 2 个）
有 `isolation` 的动作句子含「受信任执行」；没有 `isolation` 的既有用例断言**逐字节不动**。

**契约/兼容**

- `task.created` 的 `exec_policy` 变宽（+1 可选字段）：不加 required、不 bump
  `CURRENT_PAYLOAD_VERSION`（当前版本内新增可选字段，旧事件仍合法）。
  `docs/event-payload-contract.md` 同轮补字段。
- `run_command` 输出新增字段：`output` 是 open object，无需版本变更。

**风险**

## 6. 未验证（必须进验收报告）

- Windows **实机**：无；Job Object 未实现，进程树仍 `unknown`。

- 本轮不实现任何 OS 级沙箱。

## 7. 不在范围（含决策理由）

- **不实现** Seatbelt / Landlock / AppContainer / 容器：PRD F2 已定调，不写成 v1 必须交付。
- **不实现 Windows Job Object**，理由：
  1. 零依赖 stdlib `Popen` 拿不到 suspend 的线程句柄 → 只能"创建后立刻 assign"，
     assign 之前 fork 的子进程不受 Job 约束，**无法证明零逃逸**；
  2. 本项目的能力声明纪律是"可证明才能声明"：`supports_job_objects=True` 会让
     `descendants_may_survive` 变成说不清的证据；
  3. 真要做得用完整 `CreateProcess`（ctypes 重写 spawn/管道/信号），属 F1 重写级
     工单，且本机无法验证 → 另开工单，报告 §8 记录。
  → 本轮 Windows 如实保持 `supports_job_objects=False`，矩阵写 ⛔。
- **不做** per-run 后端选择（进程级；理由同 `sandbox.py` 的 `loop.py` 判据）。
- **不做** memory / 网络 / MCP 的隔离（不同域，各自工单）。
