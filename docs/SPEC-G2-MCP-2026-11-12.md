## 2 协议事实与不确定项（先说清楚证据强度）

> **本轮无法联网核验官方规范**：本机 harness 的 web provider 未注册（`web_search`
> 返回 "configured web provider auto is not registered"）。下面的事实来自对 MCP
> 2025-06-18 版规范的既有认知，**未在官方页面逐条复核**；因此实现必须按"认不出就
> 拒绝"（fail-closed）写，并且把版本号做成显式常量与诊断输出。

### 2.1 采用的最小协议面（v1 只做这些）

| 方向 | 消息 | 用途 |
|---|---|---|
| 客户端 → server | `initialize`（`protocolVersion` / `capabilities` / `clientInfo`） | 握手；协商版本 |
| 客户端 → server | `notifications/initialized` | 握手完成通知（无 id，不期待响应） |
| 客户端 → server | `tools/list`（`cursor?`） | 发现工具；按 `nextCursor` 分页直到空 |
| 客户端 → server | `tools/call`（`name` / `arguments`） | 执行工具 |
| 客户端 → server | `notifications/cancelled`（`requestId` / `reason`） | 取消；**只是请求**，不是保证 |
| server → 客户端 | `result` / `error` 响应；`notifications/*` | 只处理响应与 `cancelled` 相关；其余通知**忽略但记数** |

明确**不做**：`resources/*`、`prompts/*`、`sampling/*`、`roots/*`、`logging`、
`completion`、`progress`、`list_changed` 动态刷新、`structuredContent` 语义解释、
HTTP/SSE 传输、OAuth / 凭据转发、`outputSchema` 校验。

### 2.2 stdio 分帧

- 按 **换行分隔的单条 JSON**（每行一条消息，UTF-8，行内不得含裸换行）读写；
  **不使用** LSP 风格的 `Content-Length` 头。
- 读到的一行不是合法 JSON、或不是 JSON-RPC 2.0 形状 → 记协议错误并**让该 server
  失效**（fail-closed），不猜。
- 单条消息上限：读 1 MiB、写 1 MiB；超限按协议错误处理。

> 未核验：官方规范对"消息最大长度"是否给过硬上限。实现按上面的自有限额 fail-closed，
> 并把限额写进诊断输出（`limits` 字段），不声称这是规范要求。

### 2.3 握手与版本

- 客户端发 `protocolVersion` = 我们支持的版本；server 回它自己的版本。
- **接受集合**只放已知版本（`2024-11-05` / `2025-03-26` / `2025-06-18`）；
  回一个不在集合里的版本 → 该 server **不可用**（`mcp.protocol_version_unsupported`），
  工具**一个都不准入**，诊断里原样记 server 声明的版本。
- 握手超时（默认 10s）→ server 不可用。**不重试**、不降级、不换协议。
- `capabilities` 里我们只声明 `{"tools": {}}`（客户端不需要声明更多）；server 没声明
  `tools` 能力 → 当作"没有工具"，不报错（但要记诊断）。

### 2.4 结果与错误的三分

| 情况 | 语义 | 我们的处置 |
|---|---|---|
| JSON-RPC 响应 `result`（含 `isError: true`） | server **处理了**这次调用 | `applied`（与 `run_command` 同一口径：跑过了）；`isError` → `status=failed` |
| JSON-RPC `error`，码 ∈ {-32700, -32600, -32601, -32602} | 协议层拒绝：请求没有被当成工具调用执行 | `failed` + `none_applied` |
| JSON-RPC `error`，其他码（含 -32603 内部错误、MCP 自定义 -320xx） | server 可能在执行后失败 | `failed` + **`unknown`** |
| 超时 / 管道断开 / server 退出 / 读到畸形帧 | **不知道 server 做没做** | `failed` + **`unknown`**（红 11） |

`isError: true` 时 `effect_state` 用 `applied` 而不是 `none_applied`：server 说它失败了，
但它**已经执行过**，失败可能发生在副作用之后。

### 2.5 结果内容

- `content[]` 元素：`{"type":"text","text":...}` 收下；`image` / `audio` / `resource` /
  `resource_link` 等**不收正文**，只在 `unsupported_content` 里记类型（不静默丢弃）。
- 文本总量上限（默认 64 KiB，可配）：**客户端按 UTF-8 字节截断**，输出里标
  `bytes`（实际收到）/ `truncated` / `dropped_bytes` / `dropped_blocks`；
  **不落内容引用**（`content://`）。偏差登记：v1 原计划复用 `run_command` 的
  `stdout_ref` 机制，实现时改为"截断 + 字节记账"——为外部程序的正文引入第二套内容
  引用落盘会把"谁的正文、放多久、谁能读"三个问题一起带进来，本轮不做（§7-6）。
- `structuredContent` 是对象时原样带出（有上限，超出按截断处理并标 `truncated`）；
  不是对象 → 记 `unsupported_content`。

## 3 设计

### 3.1 信任模型（三把锁，缺一不可）

MCP server 是**用户装的外部程序**，以当前用户权限运行，v1 **不沙箱**。所以：

1. **装机（进程级配置）= 用户信任决定**：只从用户显式给的配置读 server，不读模型、
   不读任务参数、不读工作区里的文件。配置里没有任何"由模型发现"的入口。
   与 `TIANSHU_EXEC_BACKEND` 同一类边界——**谁启动进程谁负责**。
2. **任务级白名单**：任务必须显式声明允许的 server 名（`Task.mcp_servers`，
   CLI `--allow-mcp-server <name>` 可重复）。空 = 一个都不许。判在**弹批准之前**
   （与网络白名单同一条教训：不给"批了也发不出去"的批准）。与 `outbound_allow`
   同形：创建时定死、`task revise` 不可改——扩权必须是新任务。
3. **逐次人工批准**：既有 `c4.mcp_call` 恒需批准，不新增自动放行路径。

**隔离口径**：MCP server 进程**不经过** `exec_backends` 注册表（那张表的 `spawn` 是
一次性执行语义，服务不了长连接；见 §7 的边界登记）。所以：

- 不冒充"后端隔离覆盖了它"。`tool.result.output.mcp` 里写
  `spawn: {"via_exec_backend": false, "argv0": ..., "cwd": ..., "env_keys": [...], "pid": ...}`，
  让读者一眼看出这个进程不在 F2 的实测覆盖里；
- 任务的 `ExecPolicy.isolation_requires` 非空时，MCP 调用**直接拒绝**
  （`c4.mcp_isolation_unproven`），**不许**拿 `isolation.require_isolation_requirements()`
  的报告给 MCP 背书：那份报告是 **exec backend 的一次性子进程探针**测出来的，
  被测量的对象（`backend.spawn` 起的短命进程）与 MCP server（本模块自己 Popen 起的
  长连接进程）**不是同一个对象**，跨对象作证等于伪造证据。将来某个声明
  `app_container` 的 exec 后端可能让这道门"通过"，但 MCP 进程照样没被它约束——
  这正是必须拒绝而不是放行的理由（复审抓到的设计硬伤）。等 MCP 专属探针 / 把长连接
  收进后端接缝之后再谈"满足隔离要求"；在那之前 MCP 的隔离结论只能是 unsupported；
- `isolation.CAPABILITY_UNTRUSTED_LOCAL_MCP` **不在**本轮启用：它的语义是"允许
  *不可信* MCP 代码运行"，需要四边界实测证据，而 v1 没有。用户自己配置并逐次批准的
  server 不是"不可信代码自动执行"，但这条差别必须写进文档，不许含糊。**未启用 →
  `enabled_capabilities()` 的输出不变**。

### 3.2 客户端与生命周期（`src/tianshu/mcp.py`）

- `McpServerConfig`（**不可变**）：`name`（`[a-z0-9_.-]{1,64}`）、`command: tuple[str,...]`
  （argv，**`argv[0]` 必须绝对路径**，不许走 PATH 搜索）、`cwd: str`（缺省 = 数据根）、
  `env: dict[str,str]`（只允许声明；实际传给子进程的是 `PATH` + 声明项，
  **不继承** `os.environ` 的其余变量——密钥不会被顺手泄给第三方 server）、
  `timeout_ms`（握手）、`call_timeout_ms`（单次调用）、`max_result_bytes`、`max_tools`。
  校验失败 → `McpConfigError`（fail-closed，报 server 名 + 字段 + 原因）。
- `StdioServer`：
  - `subprocess.Popen(..., stdin=PIPE, stdout=PIPE, stderr=PIPE, bufsize=0)`；
  - **一个读线程**读 stdout 按行解析（Windows 上 `select` 对管道不可用，所以统一用
    线程 + `queue.Queue`）；**一个排空线程**读 stderr 进**有界**环形缓冲（最多 8 KiB，
    防止 server 狂写 stderr 把内存吃光，也防止 pipe 满导致 server 卡死）；
  - `request(method, params, timeout)`：生成自增 `id`（每 server 独立计数器），写一行，
    等队列里同 id 的响应；超时抛 `McpTimeout`；读到 EOF 抛 `McpClosed`（携带已收集的
    stderr 尾部）；收到 `id` 不匹配的响应 → 记协议错误并让 server 失效（不猜配对）；
  - `notify(method, params)`：写一行，不等待；
  - `close()`：先 `terminate()`，宽限 2s 后 `kill()`，回收线程；**幂等**。
- `McpClients`（进程级）：从配置建 N 个 server；`start_all()` 并发握手 + 发现；
  单个 server 失败**不拖累**其它 server，失败原因进 `diagnostics`；`close_all()` 在
  进程退出（`atexit` + 显式调用）时回收。
- **不重试、不自动重启**：server 崩了就是崩了，诊断里记原因，该 server 的工具下一次
  调用会得到 `unknown` 或 `dispatch.mcp_server_unavailable`。重试语义留给控制面。

### 3.3 动态工具与准入（`src/tianshu/tool_registry.py` + `toolschema` 归一）

**名字映射**（`mcp://<server>/<tool>` → 工具 id）：

- `server` / `tool` 先按资源解析器的字符集校验（`[a-z0-9_.-]{1,64}`）；不在集合里的
  server 名 → 配置期拒绝；不在集合里的 tool 名 → 该工具**不准入**（记原因）。
- 工具 id = `mcp__` + `server.translate(-.→_)` + `__` + `tool.translate(-.→_)`；
  结果必须匹配 `^[a-z][a-z0-9_.]*$`，长度 ≤ 96。
- **映射冲突**（两个 server/tool 归一后撞成同一个 id，例如 `a-b` 与 `a_b`）→
  **两者都不准入**，诊断写明冲突对。不做"先到先得"。

**schema 归一**（server 的 `inputSchema` → `toolschema` 封闭方言）：

- 允许：`type: object`（根必须有）、`properties`、`required`、`additionalProperties`
  （bool）、`items`、`minItems`/`maxItems`、`enum`、`minimum`/`maximum`（**只接受整数**）、
  `minLength`/`maxLength`、`pattern`、`title`/`description`——与
  [`tool-admission.md`](tool-admission.md) §2 的表一致。
- **拒绝整个工具**（不是丢掉那个关键字）：`$ref`/`$defs`/`definitions`/`$schema`/`$id`、
  `oneOf`/`anyOf`/`allOf`/`not`、`if/then/else`、`format`、`multipleOf`、`uniqueItems`、
  `patternProperties`/`propertyNames`/`dependentRequired`/`dependentSchemas`、
  `default`/`examples`/`deprecated`/`readOnly`/`writeOnly`、`const`、
  `minProperties`/`maxProperties`、`contains`/`prefixItems`/`unevaluatedProperties`、
  类型数组（`["string","null"]`）与浮点边界。原因写进准入记录。
- `additionalProperties` 缺省 → 归一成 **`false`**（**收窄**，不是放宽）。这是有意的：
  我们的方言要求封闭对象；server 允许的更多写法和我们允许的不一样时，**我们拒绝**，
  可核对的后果是"模型多传一个字段会被拒"，不是"偷偷放行"。收窄事实进准入记录
  （`narrowed: ["additionalProperties"]`）并进诊断。
- `required` 里出现未声明的属性 → 拒绝该工具（不猜）。
- 归一后的 schema 进 `ToolSpec.input_schema`，并**再跑一遍** `validate_registry({...})`
  的编译（注册期校验不留后门）。

**身份与版本**（红线 8：schema 变即新工具）：

- 准入记录 `McpToolBinding`：`server`、`tool`、`tool_id`、`tool_version`、`schema_hash`
  （归一后）、`raw_schema_hash`（server 原样）、`description_hash`、`narrowed`。
- `tool_version = "mcp1:" + sha256(server|tool|raw_schema|normalized_schema|description)[:16]`。
  **原样 schema 也进摘要**：server 改了一个我们本来就不认的关键字，也算换了一个工具。
- 旧批准匹配靠 `action_digest`（含 `tool_version`/`schema_hash`/`description_hash`），
  所以"server 升级了工具"→ 摘要变 → 旧批准失效 → 重新问人。**不许**热替换。
- tool 的 `side_effect_level = "non_idempotent"`、`exec_model = "E3"`、`action = exec`、
  `path_arg = ""`：MCP 工具没有可回滚的本地写前状态，按最保守的一档记。
- 描述前缀：`[MCP <server>/<tool>] <server 给的描述>`（截断到 1 KiB）。**server 给的
  描述是不可信文本**：它是提示注入面，也是审批摘要的一部分；文档与 UI 都必须这么写。

**注册表**（`ToolRegistry`）：

- 只读视图：`specs`（内置 `SPECS` + 已准入 MCP）、`bindings`（`tool_id → McpToolBinding`）、
  `ids()`、`manifest()`（模型可见投影，按 `exposed` 过滤）。
- 进程级默认注册表 = 内置 `SPECS`（**没有 MCP 配置时逐字节不变**）；`build_registry(clients)`
  生成带动态工具的新注册表；`current_registry()` / `set_registry()` / `reset_registry()`
  供 CLI/daemon 装配与测试复位（与 `exec_backend()` 同一套模式）。
- `Dispatcher` / `AgentLoop` 接受 `registry=` 参数（默认 = 进程级），**不用全局变量替
  构造参数**：多实例（CLI + 测试）同进程时不互相污染。
- 准入失败的工具**不进**注册表、**不进**模型清单，只在
  `tianshu mcp list --json` 的 `rejected_tools` 里出现（模型不能调用它，人能看到
  为什么没有它）。
- 上限：每 server `max_tools`（默认 64），全进程默认 128；超出的工具按名字排序后
  **拒绝**（记原因），不静默截断。

### 3.4 派发链路

- `KIND_MCP` 进 `EXECUTABLE_KINDS`；`resolve_scheme_resource()` 对 mcp 不再拒绝。
- `_authority_mcp(request, task, run, bindings, ref)`（**弹批准之前**，五步）：
  1. `request.tool_id` 必须是注册表里的 MCP 工具，且其 `(server, tool)` 与资源的
     两段**逐字相等**，否则 `dispatch.mcp_resource_mismatch`；
  2. server 必须在**任务白名单**里（`task.mcp_servers`），否则
     `c4.mcp_not_allowed`；
  3. server 必须在**进程配置**里且当前可用，否则 `dispatch.mcp_server_unavailable`
     （原因带上握手/崩溃诊断）；
  4. 任务声明了 `isolation_requires`（非空）→ 直接拒绝
     `c4.mcp_isolation_unproven`（理由见 §3.1：探针测的不是 MCP 进程，跨对象作证
     不可接受；等 MCP 专属探针/后端接缝落地再谈满足）；
  5. 返回 `_Authority(run, task, bindings, [], [])`（没有目录租约、没有 workspace 绑定）。
- `_resolve_target()` → `_McpTarget(uri, server, tool, tool_id)`；多资源照旧
  `c4.multi_resource`。
- `_classify_mcp` **不变**（恒需批准）。审批卡片上的目标就是 `mcp://server/tool`。
- `dispatch()` 走 `_dispatch_mcp(...)`（与 `_dispatch_network` 同构）：
  1. 已取消 → 一条消息都不发，`failed` + `none_applied` + `reason=mcp.cancelled`；
  2. 发 `tools/call`，按 `call_timeout_ms` 等响应；
  3. 结果翻译（§2.4/§2.5），`tool.result.output` 里给
     `mcp: {server, tool, tool_version, protocol_version, is_error, content, unsupported_content,
     bytes, truncated, content_ref, duration_ms, spawn}`；
  4. `_commit_result()` + **凭据**：MCP 的副作用在 server 那边，但我们知道"它跑了"，
     所以产出 `build_mcp_receipt()`：`action=exec`、`backend="mcp"`、证据
     `kind="mcp_call"`（带 `server`/`tool`/`request_id`/响应 `sha256`）+ `intent` +
     `result`，`after_state = "mcp:<sha256(server|tool|request_id|响应摘要)>"`、
     `before_state="unknown"`。
     **`verify_receipts()` 必须在 `ACTION_EXEC` 分支之前按 `backend == "mcp"` 分流**：
     现有 exec 分支（`receipt.py` 的 `verify_receipts`）会要求
     `exit_code/signal/timed_out/duration_ms/stdout/stderr/argv`，MCP 的输出没有这些
     字段，按 exec 口径核对会把**合法凭据判成损坏**（与 N4 忘记登记
     `memory_erasure` 是同一类错）。MCP 分支只核事件引用、`after_state` 形状与
     `mcp_call` 证据，**不比较磁盘**。
- 取消：`_cancel_requested(run)` 在发包前检查一次；等待中被打断 → 发
  `notifications/cancelled` 后按 `unknown` 结算（"发出去过"= 可能已执行）。
- **恢复**：MCP 工具**不进** `SPECS`，`recovery.py` 的未知工具分支天然给出
  `unknown` + 阻断目录。施工期**不改** recovery，并在验收报告里写明这是有意保留。
  （**v4 起**改为按"外发边界标记"分档，见下。）
- **外发边界标记（v4，PR #124）**：真正写 server stdin 之前，`_dispatch_mcp` 先把派发行
  从 `intent` 推进到 `executing`（`_mark_mcp_send_boundary`；只从 `intent` 推进、与
  `revoke` 共用 `execution_guard`）。恢复/`assess_run` 据此把未完成的 MCP 调用分两档：
  - 行仍是 `intent`，或已是 `revoked`/`rejected`（标记从没推进）→ 请求**一定没写出**
    → `status=failed`、`effect_state=none_applied`、`reason=mcp.not_sent`，**不阻断**；
  - 行是 `executing`，或**无从证明**（老库没有 `dispatches` 表、没有行、状态不认识）
    → `unknown` + `reason=mcp.crash_unsettled` + 阻断待核查（保守方向）。
  撤销先到 → 标记推进不上 → **不发请求**，结论是确定的 `rejected`/`none_applied`；标记
  先到 → `revoke()` 明确报错"已经开始执行"，不再假装撤销成功。`revoked`/`rejected` 是
  审计终态：恢复照写结果、**不改写**行。标记提交与真正写出之间的窄窗口仍按"可能已发出"
  保守处理（有意，见验收报告 §4-10）。
  **升级兼容**：派发表带 `boundary_protocol`（新行 1；`ALTER TABLE` 给旧行补 0）。旧版本
  写请求前不推进派发行，所以**旧行的 `intent`/`revoked`/`rejected` 不能证明没发**——一律
  `unknown` + 阻断；老库缺列时按旧行读（恢复不许崩）。
  **抢守卫超时**：标记包在 try 里，`GuardTimeout` 走 `_abort_dispatch`（`rejected` /
  `none_applied` / `dispatch.guard_timeout`）——拿不到守卫等于没发出去，不许记成
  `unknown` 去挡目录（复审第二轮整改）。

- **对象级阻断（v5，PR #125）**：阻断对象模型从"只有目录"扩成**两种**，并存、不互相替代：

  | 对象 | 键 | 登记点 | 语义 |
  |---|---|---|---|
  | 目录 | resolved 路径（`overlap_key`） | 文件写恢复、undo journal、`assess_run` | "这个目录可能被动过" |
  | MCP 对象 | `mcp://<server>/<tool>`（工具级）/ `mcp://<server>`（server 级） | 恢复判 `unknown`（键**从派发行 `target` 读**）；运行期 unknown（`-32603` / 超时 / 断线）就地落 | "这个工具可能已在 server 侧执行过" |

  两道发外核验（都记 `dispatch.mcp_object_blocked`、都是 `rejected` / `none_applied`）：
  1. `_resolve_target`（**弹批准之前**）→ `_refuse_blocked_mcp_object`，不给人"批了也发不
     出去"的批准；
  2. `_mark_mcp_send_boundary`（**执行守卫内**、紧贴 `intent → executing` 推进）→
     `ensure_object_not_blocked`，拦"判定通过之后、真正写 stdin 之前"新落下的阻断。
  两个键一起查：`(tool 级, server 级)`（`resources.mcp_block_keys`）——server 级阻断必须能
  遮住它下面全部工具，否则那条记录永远读不到。命中时派发行保持 `intent`，不会被推进到
  `executing`，事后也无法被洗成"可能已发出"。
  解除：`guard.unblock_object(log, key, reason=...)`，先写 `recovery.object_unblocked` 再
  释放权威根（与 `unblock()` 同序）；`unblock()` **不碰**对象阻断。
  升级兼容：权威库新增 `blocked_objects` 表；旧库缺表 = 空集（旧版本写不出对象阻断），
  表在但读不出 → 按已阻断处理。日志里的对象阻断事件是新增类型，旧版本不会写过，无需迁移。
  **`boundary_protocol` 只影响"能不能证明没发"，不影响对象身份**：`target` 是派发当时写下
  的原始 URI，旧行也可信（旧行同样登记对象阻断——它本来就按"可能已发出"处理）。

### 3.5 配置入口与 CLI

| 入口 | 形状 | 谁用 |
|---|---|---|
| 环境变量 `TIANSHU_MCP_CONFIG` | JSON 文件绝对路径 | daemon / host / CLI 的一个进程级入口 |
| `build_stack(mcp_servers=..., mcp_clients=...)` | 直接注入配置或已建客户端（测试用） | 装配单点 |
| `tianshu run --allow-mcp-server <name>` / `tianshu task create --allow-mcp-server <name>` | 可重复；写进 `Task.mcp_servers` | 任务白名单 |
| `tianshu mcp list [--json]` | 只读：server 状态、已准入工具、被拒工具与原因、协议版本 | 人与诊断 |

配置文件形状（`TIANSHU_MCP_CONFIG`）：

```json
{"servers": {"fs": {"command": ["/usr/local/bin/mcp-fs", "--root", "/tmp/ws"],
                    "cwd": "/tmp/ws",
                    "env": {"FS_LOG": "info"},
                    "handshake_timeout_ms": 10000,
                    "call_timeout_ms": 30000,
                    "max_result_bytes": 65536,
                    "max_tools": 64}}}
```

未知键一律**拒绝**（fail-closed，报 server 名 + 键名）。配置里不许出现 `shell`、
URL、HTTP 传输、模型可写路径。

### 3.6 契约增量（四件，全部走 `docs(contract):` 单独提交）

1. **`tool.intent.tool_id` / `tool.not_dispatched.tool_id` / `receipt.tool_id`：
   枚举 → 形状 pattern** `^[a-z][a-z0-9_.]*$`（与 `tool.result.tool_id` 已有的
   pattern **逐字相同**）。
   理由：动态工具 id 无法枚举；`tool.result` 早在 F10 就按形状收口（注释写明"红线 8：
   schema 变即新工具"）。**放宽的是数据契约，不是授权**——授权仍由注册表 +
   `action_digest` 判定。旧事件仍合法（枚举 ⊂ pattern）。
2. **`task.created.mcp_servers`：字符串数组，新写恒写（空也写）**。与
   `outbound_allow` 同一做法：能力白名单用独立字段，不塞进 `ExecPolicy`（后者描述
   「命令怎么跑」，前者描述「这个任务能用哪些外部能力」）。
   **旧行怎么办（复审纠正过一版错误说法）**：`detect_version` 只管**写入**校验；
   读取不按当前 schema 重新校验，而升级前写的 `task.created` 在旁表里就是 `v1`，
   **不会**因为缺了新键自动变 `v0`。所以真实口径是：新写必须有这个键（写入期
   `PayloadContractError` 兜住），旧行缺键时**读取侧按空元组处理**（`Task.mcp_servers`
   默认 `()`，tasks 表加列 default `''`），空 = 一个都不许——这个差别写在这里，
   免得又被写成"按 v0 读"。
   `tasks.py`（`Task` 字段 + 建/读/`to_dict` + 迁移补列）在 **PR D 所有权**内，
   不是"不用动"。`task revise` 不改它。
3. **`receipt.backend` += `"mcp"`；`receipt.evidence[].kind` += `"mcp_call"`**，并为该
   kind 加三个可选字段 `server` / `tool` / `request_id`（响应摘要复用既有 `sha256`）。
   不改就等着 N4 那个坑重演：合法凭据被判"无法识别"（当时 `memory_erasure` 漏登记
   就是这个后果）。
4. **新规则编号（6 个）**：`c4.mcp_not_allowed`、`c4.mcp_isolation_unproven`、
   `dispatch.mcp_resource_mismatch`、`dispatch.mcp_server_unavailable`、
   `dispatch.mcp_tool_unknown`、`dispatch.mcp_protocol_error`。
   三处必须**同时**改，否则封闭集会自己咬自己：
   - `rules.py` 的 `RULE_IDS`（封闭集）与 `RULE_GROUPS`（每个编号必须**恰好**属于
     一组，`tests/test_rule_ids.py` 检查划分完整）；
   - `schemas/c4/rules.json`（与 Python 侧逐字一致，有漂移判据）；
   - PRD §5.4.1 的编号表。
   **不新增** `c4.mcp_call` 之外的"判定结果类"编号（`DECISION_RULE_IDS` 不变）。

5. **`schemas/c3/event.json` 必须重新生成**：`tool.intent.tool_id` 的 pattern、
   `task.created.mcp_servers`、`receipt.backend` 的枚举、`receipt.evidence[].kind`
   的枚举都在 JSON 镜像里；只改 `event_schema.py` 会让
   `test_schema_json_mirrors_python_contract` 当场变红。生成方式与既有约定一致
   （`json.dumps(doc, ensure_ascii=False, indent=2)`，不排序键）。

## 7 诚实边界（交付后仍然不成立 / 未验证）

1. **协议事实未联网核验**（本机 web provider 不可用）：实现按 2025-06-18 已知形状，
   与**自写假 server** 对得上；**真实第三方 server 兼容性 = 未验证**。首轮验收报告
   必须写这一条，并且不接受"我们自测通过"当兼容性证据。
2. **没有沙箱**：MCP server 以当前用户权限运行，能读写任何本机文件、联网、读环境变量。
   三重锁（用户配置 × 任务白名单 × 逐次批准）降低的是"模型自作主张"的风险，
   **不是**"server 本身是恶意的"的风险。`untrusted_local_mcp` 能力**未启用**。
3. **MCP 进程不经过 `exec_backends` 注册表**（长连接 vs 一次性 `spawn` 的语义差）。
   输出里 `via_exec_backend=false` 如实标注；把长连接 spawn 收进后端接缝是后续工单。
   **推论（必须一起读）**：F2 的隔离实测报告**不能**用来给 MCP 背书——它测的是
   `backend.spawn` 起的短命探针进程，不是这个长连接 server。所以
   `isolation_requires` 非空时 MCP **一律拒绝**（`c4.mcp_isolation_unproven`），
   哪怕某个后端自称/实测 `app_container`；MCP 的隔离结论在专属探针落地前只能是
   unsupported。
4. **只做 stdio**：HTTP/SSE 传输、OAuth、远程 server 全部未做。
5. **只做 tools**：resources / prompts / sampling / roots / logging / progress 未做；
   `list_changed` 不处理（server 中途换工具不会热更新，只会让旧批准失效）。
6. **图片 / 音频 / 资源正文不收**，只记类型；**大结果不落内容引用**（截断 + 字节
   记账）。v1 明确不做图片与视频。
7. **没有字节 / token 预算维度**：MCP 调用不预占账本；server 的 CPU / 内存 / 磁盘
   占用无上限（只有结果大小与超时上限）。`subtasks`/`mcp` 维度仍是"有账本没执行器"。
8. **不支持并发**：同一 server 的调用串行；跨 run 并发只到"不互相踩"的程度（未测压力）。
8.1 **等批准期间取消不立即生效**：`tools/call` 同步阻塞，取消只在发包前检查；
   等响应期间取消要等结算（超时/返回）才生效。
9. **Windows 未实机验证**：stdio 管道与线程在 `windows-latest` 上跑（CI 里会有），
   但 Windows 本来就是已知基线红；**不许**把 CI 的绿/红当作实机证据。
10. **恢复分两档（v4）**：没越过外发边界（且行由本版本写）→ `none_applied` + 不阻断；
    越过边界/无从证明/旧行 → `unknown` + 阻断。任一种都**不**做 server 侧补偿、**不**做
    幂等重放（红线 5）。
10.1 **阻断对象有两种（v5）**：目录 + MCP 对象。对象键只从派发行 `target` 读（读不到就不
    登记，不反解工具 id）；对象阻断的解除是**人工动作**（`unblock_object`），没有自动
    判据、没有过期；粒度只到"工具/服务器"，**没有 per-call 回执**——要证明"这一次到底跑
    没跑"需要 server 侧确认协议（未做）。运行期 unknown 的对象阻断只落在本数据根日志，
    跨数据根靠下一次 `recover` 的启动补登记（不是即时）。
11. **回放只读**：回放不会重新调用 MCP；事件里也没有 server 的原始响应全文（只有
    摘要/引用）——审计能核对"调用过、结果摘要是什么"，不能还原 server 内部状态。
12. **UI 只显示审批卡片上的 `mcp://` 目标**：没有独立的 MCP 面板/服务器管理界面。
13. **`task.created.mcp_servers` 对历史行是"读取侧默认空"**，不是"迁移出旧值"：
    v1 未发布，没有需要保留的生产历史；升过级的本地库只能靠"缺键=空"这条兜住。
14. **协议版本集合是常量**：`2024-11-05 / 2025-03-26 / 2025-06-18` 之外一律拒绝；
    将来出新版本必须改常量 + 补夹具，不能靠 server 自己声明就算数。
