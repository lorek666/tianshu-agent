## C-004：既存的 IPC 发送关闭竞态

受影响版本包含原main `ccff93e79cfeb93e47e5a35012fd92fae366e941` 和I/O首提交 `4479088ecb2d161755d7ba3a89e46119c94a8b8e`，整改基于已补Host的 `72af1ae9f7a5c826b1dde568ba30005e1c4dc45d`。原main [Ubuntu job 131462988207](https://github.com/lorek666/tianshu-agent/actions/runs/43298476414/job/131462988207) 为2149 passed / 8 skipped / **2 warnings**（263.43s），首I/O提交的同名两条slow-subscriber测试也有同栈警告；不是本轮引入，也不因CI结论success就省略。

路径是 `daemon._ClientConnection._send_loop → ipc.ServerConnection.send → multiprocessing.Connection._send`。发送大帧时底层可以短写；另一个线程通过 `drop → abort → close` 将连接句柄清空。下一次循环取到None句柄，`write(None, buf)` 抛TypeError，未被daemon预期的断线分支处理。原日志与本地探针均显示发送线程最终能退出、连接已标为send_stall；**尚无daemon死亡或数据损坏证据**，本项按预期断线路径泄漏裸线程异常的P2可靠性缺陷处理，不扩大为P1或授权问题。

最小独立脚本为 `/tmp/tianshu-debug-20261113/probe_sender_close_race.py`。它起真实IPC服务及通过现有authkey认证的客户端子进程，实际 `os.write` 一段字节后用屏障固定close发生在下一次write前。只注入可发生的短写与调度，不伪造TypeError或连接对象；先前Ubuntu日志提供自然调度下的独立现场证据。原输出为 `sender_joined=true / closed=true / drop_reason=send_stall / unhandled_thread_errors=[TypeError]`，exit1（`sender-close-race-probe-red`）。修后同脚本错误列表为空，exit0（`sender-close-probe-green`）。

生产改动仅在 `ipc.ServerConnection.send`：先完成 `encode(message)`，随后捕获 `send_bytes` 的TypeError；仅在底层 `closed` 为真时抛 `ConnectionClosed`，并保留原异常cause。连接仍开时继续抛原TypeError，编码异常完全不进入捕获范围。没有在daemon外层添加宽泛吞错，也没有重试发送半帧或改变drop/事件语义。

正式回归 `tests/test_ipc_send_close.py` 包含真实子进程/短写/关闭屏障，断言sender正常join、无裸线程异常、断线异常cause是TypeError、原drop_reason保持且半帧不计为已发送；两项负控分别验证开放连接TypeError原样抛出、已关闭连接也不得掩盖消息编码TypeError。原实现 **1 failed / 2 passed**（`sender-close-tests-red`）。POSIX用例在Windows跳过，因为Windows PipeConnection不是该 `_send` 短写循环；两项负控不跳过，原有IPC真实认证、往返和关闭测试全部保留，新Windows结果仍由对应提交CI给出。

## Windows 慢测定位与能力边界
